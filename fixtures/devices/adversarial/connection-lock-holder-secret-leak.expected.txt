WHAT THIS FIXTURE SHOWS

DeviceConnection conn-0048's `exclusiveLock.holderPrincipal` is a bearer-token-shaped string
rather than an opaque user/agent identifier (compare fixtures/devices/valid/
connection-busy-with-lock-valid.json's holderPrincipal: "agent-run:wp1-device-flash-3001", which
is what a legitimate value looks like).

WHY JSON SCHEMA VALIDATION ALONE CANNOT CATCH THIS

schemas/devices/connection.schema.json's DeviceLock.holderPrincipal is `{"type": "string",
"minLength": 1}` — any non-empty string is structurally a valid principal identifier. The schema
has no way to distinguish "a stable identifier naming who holds the lock" from "a live credential
that happens to be shaped like a string," because both are, syntactically, just strings.

REQUIRED REAL BEHAVIOR (binding rule 5 — API keys encrypted at rest via Android Keystore, never
logged, never sent anywhere except the provider they belong to)

A real Device Broker implementation MUST treat `holderPrincipal` as a field that will be logged,
displayed in a lock-contention UI, and persisted in DeviceConnection history — none of which are
acceptable destinations for a live credential. Before accepting a `holderPrincipal` value (and
before logging or persisting any DeviceConnection carrying one), the implementation MUST scan for
credential-shaped substrings (known API-key prefixes such as "sk-", "Bearer ", JWT-shaped
three-segment base64url strings, etc.) and refuse to accept the value as a principal identifier —
mirroring the redaction obligation schemas/common/error.schema.json's ErrorEnvelope.detail already
carries (see fixtures/common/adversarial/error-secret-leak-in-detail.adversarial.json for that
domain's equivalent fixture). A principal identifier should be a stable, opaque, non-secret handle
(a user id, an agent-run id) — never anything that also functions as a bearer credential.
