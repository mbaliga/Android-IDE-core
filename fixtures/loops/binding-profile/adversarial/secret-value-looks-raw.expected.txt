Schema verdict: VALID against binding-profile.schema.json.
`secretReferenceId` is typed as a bare string (minLength only) — this schema cannot distinguish a
legitimate Keystore handle ID from a live-looking raw provider API key by shape alone.

Real rejection basis: CLAUDE.md binding rule 5 ("API keys: encrypted at rest via Android Keystore
... never logged, never sent anywhere except the provider they belong to") plus this schema's own
field description ("MUST NEVER carry a raw secret value") and LOOP-PKG-001's secret-like-pattern
detection class (schemas/loops/registries/loop-validation-rules.v1.json — written for package
files, but the same scanning class applies here by the same reasoning: this repo already
establishes the pattern at fixtures/common/adversarial/error-secret-leak-in-detail.adversarial.json
and fixtures/execution/adversarial/receipt-secret-leak-in-log-excerpt.adversarial.json). A value
matching a known provider key shape (e.g. 'sk-ant-...') MUST never be written into
secretReferenceId — that field is a handle into security/KeystoreSecret.kt, never the secret
itself.

Remediation: redact/reject before persisting; resolve secret.* slots to a Keystore handle ID
minted at grant time, never to the provider-issued key string.
