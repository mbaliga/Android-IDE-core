Structural validation result: PASSES schemas/workspace/reconnect-token.schema.json.
`tokenBytes` is only constrained to a loose base64/base64url-shaped character-class pattern
(`^[A-Za-z0-9+/_=-]+$`) — a real Anthropic-style API-key-looking string ("Bearer-sk-ant-api03-...")
happens to satisfy that character class too, since hyphens and alphanumerics are legal base64url
characters. JSON Schema has no "does this look like a recognizable credential format" keyword, so
this fixture is adversarial at the semantic layer only, exactly like the other three fixtures in
this directory.

Why this matters: binding rule 5 in CLAUDE.md ("API keys: encrypted at rest via Android Keystore,
never logged, never sent anywhere except the provider they belong to") is written about API keys
specifically, but a ReconnectToken's `tokenBytes` is the same CLASS of object — a bearer credential
that grants reconnect access to a provider connection without re-authenticating. If a producer ever
populates `tokenBytes` with an actual plaintext secret (a raw API key, a bearer token copy-pasted
from another system, anything an attacker could replay directly) instead of a provider-issued,
app-opaque reconnect handle, every place that is allowed to touch a ReconnectToken (logs, crash
reports, `unknownFields` round-trip, a future debug-export feature) becomes a secret-leak surface
that was never audited as one, because "ReconnectToken" does not sound like "credential" the way
"ApiKey" does.

Required behavior from a real implementation (not just structural validation):
  1. A `WorkspaceProvider` implementation MUST treat every `ReconnectToken.tokenBytes` value as
     secret material for storage and logging purposes, identical to an API key under binding
     rule 5 — Keystore-encrypted at rest, never logged (including in `ErrorEnvelope.detail`,
     which binding rule 5 already forbids for API keys — the same redaction discipline applies
     here), never included verbatim in a crash report or diagnostic export.
  2. A provider integration SHOULD issue `tokenBytes` as an opaque, provider-minted handle
     (ideally one that is USELESS outside that specific reconnect flow, e.g. single-use or
     scoped narrowly) rather than reusing or embedding a general-purpose credential directly —
     this bounds the blast radius if `tokenBytes` is ever exposed, independent of the logging
     discipline in (1).
  3. Recommended ErrorEnvelope if a redaction/logging boundary ever detects a `tokenBytes` value
     matching a recognizable credential-prefix pattern (best-effort heuristic, not a guarantee):
       code: "WORKSPACE_RECONNECT_TOKEN_LOOKS_LIKE_PLAINTEXT_SECRET"
       severity: "WARNING"
       retryable: false
       sideEffectState: "NONE"
       recoveryAction: "Re-issue this ReconnectToken from the provider's own token-issuance flow instead of embedding a raw credential; audit any place this value may already have been logged."
       userMessage: "A reconnect token appears to contain unexpected credential-like text and was not logged."
